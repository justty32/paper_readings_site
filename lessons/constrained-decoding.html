研究怎麼做？把例子接回論文

語言模型原本能接出許多文字，但程式和資料格式有硬規矩。Outlines 把正則約束表示成有限狀態機，預先建立狀態與可用 token 的索引。生成到哪裡，狀態機就走到哪裡，再遮掉不合法的下一步選項。它控制的是文字結構。〔2307.09702〕

PICARD 對 SQL 採增量解析：每一步檢查候選 token，將不被接受的候選剔除，還能利用資料表與欄位規格做守衛檢查。兩者把「寫完再退件」搬到生成當下。然而合法 SQL 仍可能查錯資料，正如句子文法正確，內容仍可能答非所問。〔2109.05093〕

本課練習：替一張借書單列出兩組檢查。第一組管欄位、日期格式與必填項；第二組管是否真有這本書、借書人是否符合需求。這是教學練習。當你能說出每個檢查究竟攔哪種錯，就比較不會把格式限制誤認成對全部內容的保證。

為什麼提早檢查

無效分支若早點剔除，就不必一直延伸到整段輸出完成才放棄；PICARD 比較了逐步檢查與完成後檢查。〔2109.05093〕

索引也有成本

Outlines 用預處理和索引減少逐步掃描，代價包含索引的記憶體需求；不是整個模型生成都變成常數時間。〔2307.09702〕

兩個容易混淆的地方
  • 能解析不代表符合使用者意圖。〔2109.05093〕
  • PICARD 的 SQL 專用檢查器不能不經改寫就套到所有語言。〔2109.05093〕

  1. Outlines

    狀態機、詞彙索引與結構限制。

    問題
    語言模型逐步生成時，如何有效限制輸出結構，而不每步掃描整個詞彙表。 〔2307.09702〕
    方法
    把約束轉成狀態機並建立詞彙索引，依當前狀態遮掉不能接受的下一個詞元。 〔2307.09702〕
    邊界
    保證範圍是可表達的文字結構，索引仍需預處理與記憶體，不能保證內容事實。 〔2307.09702〕

  2. PICARD

    增量解析與合法性邊界。

    問題
    通用語言模型生成 SQL 時容易寫出無效語句，事後過濾又需要大量候選。 〔2109.05093〕
    方法
    解碼每一步用增量解析器檢查候選詞元，配合資料表與欄位守衛剔除非法分支。 〔2109.05093〕
    邊界
    檢查器針對 SQL 與已知 schema 設計；合法可執行仍不代表查詢語意正確。 〔2109.05093〕
